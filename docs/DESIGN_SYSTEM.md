# 운영 앱 디자인 시스템

기준일: 2026-11-05, 한국 시간. 로고스의 업무·접근성 기준과 카리스가 정리한 실제 CSS 토큰을 연결하는 문서다. 변수 정의와 적용의 기준 파일은 `src/owner-ui.css`, 대상 셸은 `.app-shell`이다. 이 문서를 앱 안의 전시 페이지나 새 메뉴로 노출하지 않는다.

이 계약은 사장님 예약 캘린더·선택일 패널·방문 상세·예약/결제 폼의 일관성을 우선한다. 고객 서비스 `.public-site`는 별도 화면이며, `public/planning/`의 독립 요금표 제작 문서까지 이미 같은 시스템으로 통일했다고 표현하지 않는다. 기존 CSS 전체의 원시 값을 모두 제거했다는 뜻도 아니다. 변경하는 운영 컴포넌트는 아래 공통 토큰과 상태 규칙을 사용하고, 최종 화면의 계산된 스타일로 확인한다.

## 1. 코드 계약

- **토큰의 소유 범위:** `.app-shell` 아래에서 정의한다. 새 운영 컴포넌트는 임의의 새 분홍색·회색·반경을 만들기 전에 이 변수를 사용한다.
- **컴포넌트의 소유 범위:** `StudioCalendar`는 달력과 선택일 일정, `AppointmentDetails`는 방문의 맥락과 메모, `SettleForm`은 실제 결제 확인을 담당한다. 같은 방문 정보를 서로 다른 기본 스타일로 다시 만들지 않는다.
- **반응형 판단:** PC 일정 패널의 CSS와 컴포넌트 로직 모두 `min-width: 1100px`를 사용한다. CSS는 패널을 숨겼는데 로직은 PC 행동을 유지하는 불일치를 만들지 않는다.
- **상태는 데이터에서 결정:** 오늘/선택일, 미결제/결제 완료, 입력 중/저장 중/실패/성공은 실제 상태에서 표시한다. 꾸밈용 배지로 연결·저장을 완료한 것처럼 표현하지 않는다.
- **새 업무에는 기존 패턴 사용:** 입력 필드는 기존 라벨·힌트·오류·포커스 규칙, 저장은 비활성화·실패 초안 보존·성공 피드백 규칙을 따른다.
- **결제 날짜 선택:** `DatePicker.tsx`는 앱 안에 표시하는 달력이다. 결제일은 기본 오늘이며 `변경`을 누를 때만 열린다. 날짜 버튼·방향키·연도/월 선택을 제공하고 미래 날짜는 비활성화한다. 선택 시 결제 화면으로 돌아온다. 다른 기존 폼의 날짜 입력까지 교체한 것은 아니다.

## 3. 글자 토큰

| CSS 변수 | 값 | 사용 |
| --- | --- | --- |
| `--owner-type-caption` | `11px` | 짧은 보조 정보, 날짜 셀의 압축 미리보기 |
| `--owner-type-small` | `12px` | 필드 라벨·시간·정산 수단·메타 정보 |
| `--owner-type-body` | `14px` | 아이 이름·보호자·서비스·작업 내용·패널 금액 |
| `--owner-type-title` | `18px` | 선택일·상세 영역 제목 |
| `--owner-type-heading` | `24px` | 화면 제목, 최종 결제 합계의 강조 |

- 시스템 고딕 계열을 사용하며 사진·아이콘이 없어도 정보 위계가 유지되게 한다.
- 본문 행간은 약 1.5–1.7, 짧은 라벨은 약 1.3–1.5를 기준으로 한다. 긴 메모는 줄바꿈과 공백을 보존하고 `overflow-wrap`으로 가로 넘침을 막는다.
- PC 일정의 아이 이름과 금액은 14px 수준을 유지한다. 여러 줄을 억지로 맞추기 위해 9px 이하 텍스트를 추가하지 않는다. 공간이 부족하면 미리보기 수나 반복 정보를 줄인다.
- 모바일 입력 텍스트는 16px 이상을 사용해 실제 입력과 확대 동작을 고려한다. 화면 전체를 작게 축소해 PC 밀도를 강제하지 않는다.
- 긴 이름은 좁은 미리보기에서만 말줄임하고, 선택일 목록·상세에서는 확인할 수 있어야 한다. 금액은 잘라서 의미가 바뀌지 않게 한다.
- 숫자 비교가 필요한 금액·시간은 가능한 경우 tabular 숫자를 사용한다. 월간 압축 금액은 접근성 이름/툴팁에 전체 값을 제공한다.

모서리는 기능 위계에 따라 사용한다. 바깥 패널/시트는 경계를 구분하는 컨테이너이고, PC의 시간순 일정은 주로 행과 구분선으로 읽힌다. 모든 예약과 보조 설명을 높은 둥근 카드로 감싸지 않는다. 기존 모바일 카드와 PC 목록은 같은 업무 정보를 제공하되 동일한 컨테이너 모양을 강제하지 않는다.

## 5. 컴포넌트 계약

### 월간 캘린더

- 읽기 순서: 날짜 → 건수·금액 → 시간·아이 미리보기.
- PC 미리보기는 셀 높이에 따라 3개/2개/1개/0개로 조절하고, 필요한 경우 초과 개수를 표시한다. 글자 크기를 계속 낮춰 많은 줄을 고집하지 않는다.
- 개별 셀에 반복 '매출' 라벨이나 정산/취소 버튼을 넣지 않는다.
- 단일 클릭/방향키는 날짜 선택이다. 등록·결제 데이터는 변경하지 않는다.
- 선택일 목록은 PC 우측 패널, 모바일 날짜 시트에서 표시한다.

### PC 선택일 패널

- 날짜·건수·날짜 이동을 한 줄 60–72px 헤더로 표시한다. 패널의 고정 부분은 높이의 20% 이하, 본문 스크롤은 80% 이상을 목표로 한다.
- 큰 등록 버튼, 상단 설명 문장, 높은 금액 카드의 반복을 만들지 않는다. 결제/예약 금액은 작은 행으로 구분한다.
- 우하단 `＋`는 현재 선택일의 등록 폼을 연다. 접근성 이름으로 날짜와 동작을 식별한다.
- 목록 마지막의 정보와 행동 버튼이 `＋` 밑에 가리지 않도록 충분한 하단 스크롤 여백을 둔다.

### 방문 상세와 메모

- 방문 대상·보호자·일정·서비스/작업 맥락이 금액 상세보다 먼저 읽혀야 한다.
- 예약 당시 저장된 정보와 현재 고객대장 참고사항을 구분한다. 아이의 건강/행동/스타일 메모, 보호자 메모, 이번 방문 메모는 서로 다른 출처다.
- 방문 메모 저장은 해당 예약의 `notes`만 변경한다. 정산/취소 후에도 메모만 수정할 수 있으나 금액·일정·상태 잠금은 유지한다.
- 고객 공유물에 내부 대장 메모를 자동 포함하지 않는다.

### 입력과 검색

- 라벨은 항상 보이게 하고 예시/placeholder로 대체하지 않는다. 필수·단위·허용 범위를 필요한 위치에서 알려준다.
- 고객 검색 결과는 `보호자명 | 반려동물 이름 | 연락처 끝 4자리`로 표시한다. 검색 결과 없음·선택·연결 해제·직접 입력도 같은 경계/글자 규칙을 사용한다.
- 입력 실패는 해당 작업의 오류 영역에서 설명하고 입력을 보존한다. 성공 색이나 저장 완료 토스트와 섞지 않는다.

### 결제 확인

- 아이/보호자·방문 서비스/작업·최종 금액을 확인하고 카드/현금/계좌이체 중 수단을 선택한다.
- 오늘 날짜가 기본이며 `날짜 변경`에서만 날짜 입력기를 연다.
- 요금 상세/기본요금·추가요금 편집은 접힌 영역으로 제공한다. 합계는 변화에 따라 갱신하되, 결제 기록 전에는 서버에 부분 저장하지 않는다.
- 명시적 기록 버튼을 눌러 검증·저장한다. 실제 결제 게이트웨이가 아닌 수동 기록임을 넘어서는 기능을 암시하지 않는다.
- 등록·상세·메모와 같은 필드/버튼/오류/저장 중 토큰을 사용한다.

## 6. 상태와 인터랙션

| 상태 | 화면 계약 |
| --- | --- |
| 기본 | 읽을 수 있는 본문색, 행동과 단순 정보의 구분 |
| Hover | 배경/경계의 작은 변화. 문구나 금액을 이동시키지 않음 |
| Focus | 키보드 사용자가 현재 대상을 찾을 수 있는 연속된 외곽선. 배경색 변화만으로 대체하지 않음 |
| 선택 | 날짜·결제 수단·검색 결과의 실제 선택과 `aria-pressed` 등 상태 속성 일치 |
| 비활성화 | 명확한 disabled 상태. 클릭되는 것처럼 hover 효과를 제공하지 않음 |
| 저장 중 | 중복 제출 차단, 버튼/폼의 처리 중 안내, 입력한 내용 유지 |
| 실패 | 오류 이유 표시, 초안 보존, 재시도 가능. 성공 토스트 금지 |
| 성공 | 데이터 갱신 후 짧은 성공 피드백. 중복 금액이나 중복 기록을 만들지 않음 |
| 빈 상태 | 어떤 날짜/목록이 비었는지 짧게 표시하고 현재 작업의 진입점을 제공 |

색·경계 등 단순 피드백은 약 150ms, 선택일/화면의 내용 전환은 약 180ms 수준으로 짧게 유지한다. `prefers-reduced-motion: reduce`에서는 불필요한 이동·재등장 모션을 생략한다. 화면 전환 때마다 정보가 크게 밀리거나 전체 달력이 반복해서 나타나는 효과를 넣지 않는다.

## 7. 반응형과 접근성 검증

- **1100px 이상:** PC 월간+선택일 패널. 같은 기준을 JS와 CSS에서 사용한다.
- **761–1099px:** 캘린더 폭을 우선하고 일별 상세는 시트로 표시한다. 두 패널을 무리하게 줄여 붙이지 않는다.
- **760px 이하:** 기존 월간 중심 모바일 화면과 하단 내비게이션/상세 시트. PC 셀의 예약 미리보기를 억지로 넣지 않는다.
- **검증 크기:** 1440px PC, 1100px 경계, 중간 태블릿, 390/320px 모바일, 6주짜리 달력과 높이 667px의 작은 화면. PC도 낮은 높이에서 고정 헤더/스크롤 비율과 내용 잘림을 확인한다.
- **읽기 대비:** 일반 정보 텍스트는 배경 대비 4.5:1, 충분히 큰 텍스트는 3:1 이상을 검증 기준으로 삼는다. 포커스·필수 아이콘 등 조작 대상을 식별하는 시각 신호도 주변과 구분돼야 한다. 토큰이 있다고 자동 준수로 표시하지 않고 실제 foreground/background 조합을 측정한다.
- **조작 크기:** 모바일 버튼/터치 대상은 44px 안팎 이상의 조작 영역을 기본으로 한다. PC의 밀집 아이콘도 실제 클릭 영역과 충분한 간격을 유지한다. 아이콘 그림 크기와 클릭 영역을 같은 값으로 줄이지 않는다.
- **확대/긴 내용:** 브라우저 확대, 긴 아이·보호자 이름, 긴 메모, 큰 금액에서 가로 넘침·중첩·손실이 없어야 한다.
- **키보드:** 달력 이동·등록·상세·검색·수단 선택·저장·Escape 닫기가 마우스 없이 가능하고, 숨겨진 패널의 버튼은 탭 순서에 남지 않는다.
- **화면 낭독:** 조회하는 날짜·금액 기준·저장 상태를 텍스트/속성으로 알 수 있어야 한다. 색이나 애니메이션만으로 변경을 전달하지 않는다.

## 8. 적용·리뷰 방법

토큰 정의 → 해당 컴포넌트의 상태 적용 → 실제 화면/동작 확인 순서로 검토한다. 새 화면마다 별도의 색·여백·버튼을 복사하지 않는다. `owner-ui.css`는 기존 스타일 위에서 적용되는 운영 앱의 기준이며, 같은 selector에 다른 값이 중복되면 마지막 값만 보고 문서화하지 말고 계산된 스타일과 영향 범위를 확인한다.

브라우저 검증에는 캘린더 날짜/금액/선택, 패널 공간, 마지막 행의 FAB 가림, 방문 상세의 대장 메모, 결제 날짜 변경·수단 선택·요금 변경·메모 저장·중복/실패 처리, 모바일 검색·제품 선택을 포함한다. 자동 테스트 통과는 실제 매장 사용자 평가를 대신하지 않는다. 자료나 데모를 직접 확인하지 않은 경쟁 앱의 UI를 분석했다고 보고하지 않는다.
