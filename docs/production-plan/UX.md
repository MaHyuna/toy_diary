# 업무 흐름 중심 UI/UX 설계

2026-11-05 · 제안 v1 · 구현 전 · [시안 열기](preview.html)

## 1. 설계 기준

앱이 ‘기능을 가진 화면의 모음’보다 한 방문의 흐름을 이어 주도록 설계한다. 예쁘게 보이는 카드 개수보다 사장님이 예약 전화 중 고객을 찾고, 미용 후 사진과 주의사항을 남기고, 정확히 결제를 기록하는 데 필요한 행동 수를 우선한다. 새 테마는 기존 디자인 유지 가정 없이 평가하되 금액·상태·공개 범위는 외관보다 먼저 일치시킨다.

시안은 가상 데이터로 만드는 방향 검토용이다. 예약·결제·로그인·사진 업로드·저장은 실제로 실행하지 않는다. 경쟁 앱 실측이나 사용자 테스트를 완료했다는 의미가 아니다.

## 2. 정보 구조

| 사장님 상위 메뉴 | 그 안의 업무 | 사용 시점 |
|---|---|---|
| 예약 | 월/주/일 보기, 오늘 일정, 신청함, 예약 상세 | 아침 확인·예약 전화·방문 진행 |
| 고객 | 검색 대장, 보호자/아이, 주의사항, 지난 방문·사진 | 전화 중 고객 식별·미용 전 확인 |
| 장부 | 미결제, 결제 내역, 지출, 일/월 합계 | 인계·마감·월 정리 |
| 매장관리 | 게시 요금표, 공지 게시판, 영업시간/휴무, 계정 연결, 운영 상태 | 요금 변경·휴무·고객 연결 |

| 고객 상위 메뉴 | 주요 내용 | 진입 |
|---|---|---|
| 요금 | 현재 게시 요금, 서비스/견종/체중 조건, 상담 필요 안내 | 비로그인 가능 |
| 예약 | 서비스/아이 조건 → 가능 시간 → 신청 확인·결과 | 신청 시 최소 정보·동의, 확정 상태 구분 |
| 미용수첩 | 로그인/연결 상태, 아이 선택, 전후 사진, 체중, 소견, 집에서 관리 | 자기 계정의 승인된 아이만 |

첫 방문 고객은 매장/요금·예약 신청에 쉽게 진입한다. 로그인한 기존 고객은 ‘우리 아이 + 다음 예약 상태 + 최근 미용 기록’을 우선 본다. 앱 내부 기본 주소/재방문 진입 정책은 권한별로 정의하며, 관리자 화면을 고객의 탐색 메뉴에 섞지 않는다. 시안 상단의 역할 전환은 **설계 검토 도구**이며 제품의 권한 전환 UI가 아니다.

## 3. 대표 시나리오와 화면 계약

### A. 전화로 예약 잡기

달력의 날짜/시간 선택 → 예약 등록 패널 → 사진과 `보호자 | 아이 | 연락처 끝 4자리`로 검색 → 주의사항/지난 미용 요약 → 서비스·체중·스타일 → 서버 견적/상담 필요 → 날짜/소요시간 → 저장.

- PC: 목록을 가리지 않는 우측 작업 패널. 모바일: 전체 화면 입력, 상단 뒤로, 하단 단일 저장 행동.
- 고객 검색과 아이의 위험 정보가 금액 입력보다 먼저 나온다. 주의사항 전체를 처음부터 긴 폼으로 펼치지 않는다.
- 선택 날짜/시간은 그대로 이어진다. 저장 성공 후 해당 날짜 일정이 갱신된다. 실패 시 입력 보존.
- ‘등록’은 확정 예약 생성, 고객 ‘신청 접수’와 상태 문구를 구분한다.

### B. 고객 신청 받기

고객: 요금 조건 확인 → 가능한 시간 → 아이/연락 정보 → 가격과 개인정보 동의 확인 → 신청 접수 → 확정 대기.

사장님: 예약 신청함에서 날짜·아이·서비스·견적·신규 여부 확인 → 기존 대장 연결/신규 고객 생성 검토 → 시간 충돌 재검사 → 확정/거절.

미승인 신청이 영구적으로 시간을 막지 않도록 보류 만료 정책을 둔다(제안: 30분, 매장 운영 방식에 따라 확정). 고객 화면에 만료/변경/확정 대기 문구를 구분한다. 현재 익명 신청을 계정의 본인 예약으로 자동 귀속시키지 않는다.

### C. 미용 → 기록 → 인계

오늘 일정 행 선택 → 아이·보호자·주의사항 확인 → 미용 시작/완료 → 전후 사진·체중·미용 소견·집에서 관리 작성 → 고객에게 보여줄 내용 미리보기 → 공개 → 결제 기록 → 다음 방문 참고.

- 미용 완료·결제 완료·고객 공개는 별개의 상태와 행동이다. 미용 완료했지만 미결제인 방문을 표현할 수 있어야 한다.
- 내부 참고 메모와 고객 전달 소견을 시각적으로 분리. 내부 메모는 자동 복사/게시하지 않는다.
- 사진은 촬영일·전/후 구분·업로드 진행/재시도·서버 저장 확인 제공. 완료 없이 창을 닫아 사진이 저장됐다고 오인하지 않게 한다.
- 고객 공개 전 화면 그대로 미리보기. ‘초안 저장’과 ‘고객에게 공개’의 의미를 명확히 구분한다.

### D. 결제 기록·마감

방문 상세/미결제 목록 → 아이·최종 금액·추가 작업 사유 확인 → 수단(카드/현금/계좌이체) → 오늘 기준 결제일 → 기록 확인.

- ‘결제 기록’은 실제 PG 청구가 아님을 제품 문구로 혼동시키지 않는다.
- 캘린더의 날짜 기준 예약금액과 결제일 기준 받은 금액을 혼합하지 않는다. 합계마다 기준은 한 번만 명시한다.
- 이미 기록한 결제는 일반 편집으로 덮어쓰지 않는다. 중복 클릭/통신 재시도는 같은 결과를 반환한다.
- 환불/부분결제가 초기 운영에 필요한지 확인하고, 필요하면 정식 원장 정책으로 우선 구현한다. 임의 음수 지출로 대신 처리하지 않는다.

### E. 요금 변경

매장관리 → 요금표 → 고객과 같은 표를 편집 → 변경 전/후 비교 → 고객 미리보기 → 게시 버전 생성.

- PC는 몸무게 행×서비스 열, 모바일은 비교 가능한 축 전환/소단위 표를 사용한다. 페이지 가로 스크롤을 요구하지 않는다.
- 구조/금액 편집 UI와 고객 HTML은 동일한 데이터를 사용하는 공통 렌더러. 디자인 편집은 로고·색·폰트·테두리 같은 표현만 담당한다.
- 요금 초안 저장이 곧 고객 게시가 되지 않는다. 게시 전 신규 예약에 적용될 금액을 확인한다.
- 기존 예약/결제는 당시 견적 버전을 유지한다. 변경된 값을 과거 방문에 소급하지 않는다.

### F. 보호자의 재방문

로그인 → 연결 대기 또는 우리 아이 선택 → 다음 예약 상태/최근 방문 → 미용 전후 사진 → 방문별 체중 → 소견/집에서 관리 → 다음 예약.

고객에게 기록 링크 복사/붙여넣기를 기본 행동으로 요구하지 않는다. 링크는 선택적 전달 경로다. 다른 아이로 전환하면 방문·사진·체중이 모두 그 아이 범위로 바뀌어야 한다. 연결 해제 후 이전 탭에서도 다음 조회는 거절되어야 한다.

## 4. 모바일/PC 레이아웃

| 화면 | PC | 모바일 |
|---|---|---|
| 예약 첫 화면 | 월간 달력 + 열고 닫을 수 있는 선택일 패널, 실제 업무 공간 우선 | 월간 달력 먼저, 날짜 선택 시 선택주+시간순 일정; 추가는 우하단 한 개 |
| 예약 상세/등록 | 충분한 너비의 작업 패널, 기존 목록 맥락 유지 | 전체 화면, 하단 행동이 키보드/안전 영역과 겹치지 않음 |
| 고객 대장 | 사진·아이·보호자·연락처·주의·최근/다음 방문의 밀집 표 | 사진·아이/보호자·주의·최근 방문 중심의 간결한 행, 상세에서 전체 확인 |
| 장부 | 미결제/받은 결제/지출 탭, 일자·내역·수단·금액 표 | 필수 비교 열 유지, 긴 세부사항은 행 상세. 의미 없는 카드 재포장 금지 |
| 요금표 | 표 전체 구조·초안/게시 차이 확인 | 모든 금액을 읽을 수 있는 분할 표. 작은 이미지 확대를 기본 탐색으로 쓰지 않음 |
| 공지 관리 | 제목·공개 상태·수정일 목록, 글별 조회/작성 | 검색/필터+게시글 목록, 작성은 페이지. 모달 하나에 여러 글 편집 금지 |
| 고객 수첩 | 아이 요약과 방문 이력/기록을 함께 | 아이 선택→최근 기록 순서, 사진/관리 소견의 읽기 흐름 우선 |

닫기와 예약 취소를 구분한다. `일정 닫기`는 읽기 패널만 닫는다. `예약 취소`는 텍스트와 확인 절차를 가진 업무 행동이다. `수정`, `공개 해제`, `결제 기록` 등 중요한 행동을 의미 불명확한 아이콘으로 줄이지 않는다.

## 5. 공통 디자인 시스템 제안

### 표현 방향

차분한 웜 화이트·차콜 본문·짙은 청록 행동색·세이지 보조색을 기본 후보로 제시한다. 동물 사진은 아이 식별과 미용 결과에 사용하며 큰 장식 이미지로 업무 영역을 소비하지 않는다. 화면마다 보라/초록/분홍 테마를 다시 만들지 않는다. 고객용은 같은 토큰을 쓰되 여백과 사진의 비중을 늘린다. 매장의 요금표 출력 테마는 별도이고 앱의 테마와 동일할 필요는 없다.

| 토큰 | 후보 값 / 규칙 |
|---|---|
| 바탕 / 표면 | `#F5F5F0` / `#FFFFFF` |
| 본문 / 보조 본문 | `#202E2A` / `#596861` |
| 주 행동 / 밝은 보조 배경 | `#245D4A` / `#EAF1E8` |
| 구분선 / 위험 행동 | `#DFE4DE` / `#A43E3E` |
| 본문 글꼴 | 시스템 한글 sans, 장식 글꼴은 출력물에 제한 |
| 글자 크기 | PC 본문 14–16, 모바일 입력 16 이상, 보조 12–13, 제목 22–28 |
| 간격 | 4/8/12/16/24/32. 같은 의미의 행/필드에 같은 간격 사용 |
| 형태 | 입력/버튼 radius 8, 패널 12, 표는 행 구분선. 카드/그림자 남용 금지 |
| 터치 / 밀도 | 모바일 중요 행동 최소 44px, 표 숫자는 tabular-nums·오른쪽 정렬 |
| 움직임 | 120–180ms 단순 상태 전환. reduced-motion 지원 |

### 공통 컴포넌트

AppShell(role), Navigation, PageHeader, DataTable/CompactRow, CalendarCell/AgendaRow, CustomerSearch, Field/FieldError, StatusBadge, Money, PhotoPair, VisitTimeline, PriceMatrix, PublishPreview, InlineNotice, SubmitBar, ConfirmAction, Empty/Error/LoadingState.

디자인 토큰 → 상태 명세 → Story/독립 검증 → 업무 화면 하나에 적용 → 회귀 확인 순서. CSS는 토큰·컴포넌트·레이아웃·화면 예외로 나누고, 기존 전역 스타일 위에 무한 override를 덧붙이지 않는다. 교체 중 화면은 경계를 두어 점진 적용한다.

### 상태와 접근성

모든 핵심 화면에 로딩·빈 결과·오류/재시도·작성 중·저장 중·성공·권한 없음·연결 끊김 상태를 정의한다. 실패와 오래된 데이터는 서로 구분한다. 서버 검증 전 성공 토스트 금지. 저장 버튼 중복 차단만으로 서버 멱등성을 대신하지 않는다.

읽기 대비 4.5:1(큰 글자 3:1), 키보드 순서/포커스 복원, 라벨 유지, 색 외의 상태 문구, 200% 확대와 긴 한글 이름/메모, 모바일 키보드와 안전 영역, 스크린리더의 날짜/금액/진행 상태를 검증한다. 시안의 색 후보가 있다고 접근성 통과로 판정하지 않는다.

## 6. 화면별 성공 기준과 사용자 검토

| 작업 | 기준 제안 |
|---|---|
| 기존 고객 전화 예약 | 검색→확인→시간/견적→등록, 동일 정보 재입력 없음 |
| 당일 업무 확인 | 선택 날짜·예약 건수·금액 기준을 바로 구분, 닫기/취소 혼동 없음 |
| 미용 후 인계 | 전후 사진·체중·보호자 관리 안내를 한 방문에서 저장/공개 |
| 결제 | 미용 완료·미결제 구분, 중복 기록/과거 금액 변경 없음 |
| 고객 가격 확인 | 견종/몸무게 조건과 금액을 확대·좌우 스크롤 없이 확인 |
| 고객 수첩 | 로그인/연결 후 링크 입력 없이 자기 아이의 공개 기록 열람 |

검토는 실제 사장님이 가상 시나리오 5개를 수행하는 방식으로 진행한다. 소요 시간·멈춘 위치·뒤로 간 횟수·오입력·상태 해석을 기록하고 구현 우선순위에 반영한다. 아직 사용성 성과 수치를 달성했다고 주장하지 않는다.

## 7. 시안 범위

`preview.html`은 사장님 예약/고객/장부/매장관리, 고객 요금/예약/수첩의 방향을 보여준다. PC·모바일 검토 폭을 바꾸고, 날짜/메뉴/예약 작업/고객 역할을 전환할 수 있다. 실제 권한·견적·동기화·저장 코드는 연결하지 않았다. 기존 앱을 교체하지 않으며 게시하지 않았다.
