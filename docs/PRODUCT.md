# 몽글 — 1인 애견미용실 운영 웹앱 기획

## 목표와 사용자

고객관리대장, 예약장, 장부를 따로 작성하는 1인 애견미용사가 반려견별 특이사항과 방문 이력, 하루 일정, 샴푸 사용 비용, 받은 돈과 매장 지출을 한곳에서 확인하도록 돕습니다. 첫 버전의 사용자는 매장 운영자 한 명입니다. 이후 직원 여러 명을 지원할 수 있도록 예약에 담당자를 구분해 저장하며, 직원 관리·권한 화면과 고객이 직접 예약하는 공개 서비스는 후속 개발 범위입니다.

외부 업종 자료는 네트워크 차단으로 본문을 검증하지 못했습니다. 아래 내용은 사용자가 확정한 요구사항과 그에 따른 설계이며, 업계 전체의 표준 절차를 검증한 결과는 아닙니다. 접근 시도와 근거의 범위는 [업무 조사 기록](RESEARCH.md)에 남깁니다.

## 기본 업무 흐름

1. **매장 기준 설정:** 서비스별 기본가·소요 시간, 견종별 추가금, 체중 구간별 추가금을 매장에 맞게 설정합니다. 처음 제공하는 기본 서비스는 예시이며 견종·체중 규칙은 빈 상태입니다. 샴푸도 실제 제품의 기준 구매금액·용량으로 등록합니다.
2. **고객 등록·상담:** 보호자와 반려견을 고객관리대장에 등록합니다. 한 보호자에게 여러 반려견을 연결하고, 견종·몸무게와 미용에 필요한 주의사항·선호 스타일을 기록합니다.
3. **예약 등록:** 등록된 반려견을 선택하거나 예약 정보를 직접 입력합니다. 서비스, 날짜, 시작 시간, 소요 시간, 견적, 특이사항을 기록합니다. 입질·엉킴·추가 작업 등은 사유와 금액을 항목별로 추가합니다.
4. **일정·방문 상태 확인:** 선택한 날짜의 예약을 시간순으로 확인합니다. 한 사람이 담당하므로 취소되지 않은 예약의 시간이 겹치면 등록·수정을 막습니다. 당일 작업량이나 몸무게가 다르면 정산 전에 관련 견적 항목과 메모를 수정합니다.
5. **목욕·미용 기록:** 예약에 사용한 샴푸와 원액 사용량, 필요시 고객 추가요금, 작업 메모를 남깁니다. 샴푸 원가는 참고 자료로 계산합니다.
6. **일정 변경·정산:** 미결제 예약의 시간과 내용을 수정하거나 취소할 수 있습니다. 작업 후 실제 결제 수단·결제일을 기록하면 완료·결제 완료 상태가 되고 장부에 매출이 반영됩니다.
7. **지출 기록:** 샴푸 구매, 임대료, 소모품 등 실제 지출을 날짜·분류·금액·메모와 함께 입력합니다.
8. **수익·재방문 확인:** 월별 실제 결제액, 지출, 차액을 확인하고 장부를 CSV로 내보냅니다. 고객관리대장에서 반려견별 방문 기록을 조회해 다음 상담에 참고합니다.

## 첫 버전의 규칙

| 항목 | 기준 |
| --- | --- |
| 매장·담당자 | 매장 하나, 현재 운영자 한 명. 예약에 담당자 ID 저장 |
| 고객·반려견 | 보호자 한 명에 여러 반려견 연결, 예약과 반려견 ID로 이력 연결 |
| 요금표 | 서비스 기본가·시간 + 견종별 추가금 + 체중 구간별 추가금 |
| 견적 | 요금표로 구성한 항목을 예약에서 조정하고 사유별 추가금 기록 |
| 견적 보존 | 예약별로 당시 금액·내역을 저장하며 이후 요금표 변경과 분리 |
| 샴푸 사용 | 제품과 원액 사용량으로 원가 계산, 고객 청구액과 별도 기록 |
| 샴푸 장부 | 구매 시 실제 지출 기록, 사용 원가를 지출에 중복 반영하지 않음 |
| 일정 | 시작 시간과 소요 시간으로 종료 시간 계산, 자정을 넘는 예약은 지원하지 않음 |
| 예약 상태 | 예약, 완료, 취소 |
| 결제 상태 | 미결제, 결제 완료 |
| 매출 시점 | 예약일이 아닌 실제 결제일 |
| 금액 | 원 단위 정수 |
| 중복 결제 | 같은 예약을 두 번 정산하지 못하게 처리 |
| 결제 완료 예약 | 수정·취소 제한, 환불은 후속 기능 |
| 비용 | 운영자가 입력한 지출만 집계 |
| 수익 표시 | 결제액 − 지출액. 세무상 순이익이나 통장 잔액을 보장하지 않음 |
| 저장 | 로컬 SQLite, 예약·장부 샘플 데이터 없음 |

예약 당시 예상 금액과 실제 받은 금액이 다르면 **정산 전에 견적 항목을 수정**합니다. 기본가, 견종·체중 추가금, 사유별 추가금, 샴푸 고객 추가요금의 합계가 예약 금액과 일치하는지 서버에서도 확인합니다. 선금·부분 결제·환불·카드사 입금 대사는 후속 범위입니다. 반려견 특이사항에는 미용에 필요한 정보를 중심으로 기록합니다.

## 고객관리대장

보호자는 이름·연락처·메모를, 반려견은 이름·견종·몸무게·생년월일·성별·중성화 여부·알레르기·건강 주의점·행동 주의점·선호 스타일·권장 방문 간격을 기록합니다. 모르는 정보를 임의로 채우지 않습니다. 건강 정보는 보호자에게 전달받은 내용과 미용상 주의사항을 기록하며 진단 기능은 제공하지 않습니다.

예약에는 `customerId`·`petId`와 함께 당시 반려견 이름·보호자 정보·몸무게·서비스·금액을 저장합니다. 고객대장을 나중에 수정해도 과거 예약 내용이 일괄 변경되지 않습니다. 기존에 고객 연결 없이 기록한 예약은 운영자가 명시적으로 반려견을 선택해 이력에 연결할 수 있습니다. 결제 완료된 예약도 이 연결은 가능하되 과거 예약 스냅샷과 금액은 보존합니다.

## 샴푸 제품과 원가

제품에는 이름, 기준 구매금액(원), 원액 용량(mL), 제조사 지침을 확인해 입력한 희석 비율, 메모를 저장합니다. 예시 제품 가격이나 권장 희석률을 자동으로 제공하지 않습니다. 희석 비율은 `샴푸 원액 1 : 물 N` 형식의 참고 정보이며 `0`은 비율 미등록을 뜻합니다. 미등록을 원액 그대로 사용하라는 지시로 해석하지 않습니다.

예약에는 사용한 제품, **원액 사용량(mL)**, 당시 제품명·기준 단가·용량, 추정 원가, 고객 추가요금을 별도로 저장합니다. 원가는 `기준 구매금액 ÷ 원액 용량 × 원액 사용량`을 원 단위로 반올림합니다. 이미 원액 사용량을 받으므로 희석 비율로 다시 나누지 않습니다. 제품 기준 가격을 바꿔도 이전 예약에 저장된 원가는 유지합니다.

월별 샴푸 원가는 해당 월에 결제한 예약의 사용 원가를 합한 참고 지표입니다. 원가가 기록되었다고 가계부 지출이나 재고 차감이 자동 발생하지 않습니다. 실제 샴푸 구매 금액은 지출에 직접 기록하고, `정산 매출 − 기록한 지출` 계산에서 사용 원가를 다시 빼지 않습니다. 창고 수량·입출고·발주 관리는 후속 범위입니다.

## 요금과 담당자 확장 기준

견적 합계는 `서비스 기본가 + 견종 추가금 + 체중 추가금 + 사유별 추가요금 합계 + 샴푸 고객 추가요금`입니다. 예를 들어 기본가 60,000원, 견종 추가금 10,000원, 체중 추가금 5,000원, 엉킴 추가금 10,000원, 샴푸 고객 추가요금 5,000원이면 총 90,000원입니다. 이 금액은 설명용 예시이며 업계 표준 요금이 아닙니다.

요금표와 예약 견적은 분리합니다. 요금표는 새 견적의 기준이고, 예약에는 당시 적용한 항목과 금액을 저장합니다. 실제 작업량이 달라지면 정산 전에 각 항목을 조정하며, 추가 비용은 사유를 함께 남깁니다. 정산이 끝나면 견적과 결제 금액은 잠급니다.

예약의 `staffId`는 현재 `owner`를 사용합니다. 이후 직원 기능을 만들 때 직원 목록, 담당자 선택, 직원별 겹침 검사·휴무·업무 권한을 연결합니다. 담당자 ID가 있다는 이유만으로 현재 여러 직원이 동시에 예약을 받거나 로그인할 수 있는 것은 아닙니다.

## 완료 기준

- 예약을 저장한 뒤 새로고침해도 내용이 남아 있습니다.
- 보호자 한 명에게 여러 반려견을 등록하고 반려견별 예약 이력을 구분할 수 있습니다.
- 고객대장을 수정하거나 기존 예약을 반려견 이력에 연결해도 과거 예약의 정보·금액은 보존됩니다.
- 반려견의 주의사항·선호 스타일을 고객대장에서 확인할 수 있습니다.
- 요금표에서 서비스·견종·체중 규칙을 저장하면 새 예약 견적에 반영됩니다.
- 요금표를 수정해도 이미 저장한 예약의 견적 내역과 금액은 유지됩니다.
- 입질·엉킴·추가 작업 등 여러 추가금 항목을 기록할 수 있고 합계가 예약 금액과 일치해야 합니다.
- 정산 전에는 견적을 조정할 수 있고 정산 후에는 수정할 수 없습니다.
- 샴푸 원가는 원액 사용량으로 계산하고 제품 기준 가격 변경 후에도 이전 예약 기록은 유지됩니다.
- 샴푸 고객 추가요금은 견적·매출에 반영되며, 사용 원가는 구매 지출과 중복 차감되지 않습니다.
- 기존 예약과 일부 또는 전체 시간이 겹치면 이유를 안내하고 저장하지 않습니다. 앞 예약 종료 시각에 시작하는 예약은 허용합니다.
- 취소한 예약은 새 예약을 막지 않으며 매출에도 포함되지 않습니다.
- 정산한 예약은 매출에 한 번만 반영됩니다.
- 10월 예약을 11월에 결제하면 11월 매출에 반영됩니다.
- 지출을 추가하거나 삭제하면 해당 월의 지출·차액이 함께 바뀝니다.
- 입력 오류와 서버 오류가 발생하면 성공으로 표시하지 않고 내용을 안내합니다.
- CSV 내보내기에는 선택한 기간의 기록과 금액이 포함됩니다.

## 후속 개발 순서

1. **실사용 기반:** 로그인, 매장별 데이터 분리, 백업·복구, 개인정보 접근 제어. 여러 기기에서 사용하려면 이 단계와 서버 배포가 필요합니다.
2. **정산 확장:** 예약금·부분 결제·환불, 할인, 결제 수단별 집계, 카드 수수료·실입금 확인.
3. **직원·예약 확장:** 직원 등록·권한·담당자별 일정, 휴무·영업시간, 재방문 알림, 샴푸 재고·발주 관리.
4. **네이버 예약 연동:** 사용 가능한 공식 연동 방식과 필요한 사업자 승인·권한을 확인한 뒤 구현합니다.

## 네이버 예약 연동을 위한 준비

예약에 `source`와 `externalId`를 두어 직접 등록과 외부 예약을 구분합니다. 현재 예약 출처는 `manual`이고 외부 예약 ID는 비어 있습니다. 외부 서비스의 응답 형식은 별도 연동 모듈에서 내부 예약 형식으로 변환합니다.

연동 구현 시에는 다음을 결정합니다.

- **접근 권한:** 해당 매장이 사용할 수 있는 공식 API·파트너 연동 경로와 승인 조건을 먼저 확인합니다. 일반 공개 API나 즉시 연결 가능성을 전제로 하지 않습니다.
- **중복 방지:** 매장·출처·외부 예약 ID 조합으로 동일 예약이 반복 수신되어도 한 건만 유지합니다.
- **변경·취소:** 외부 변경을 반영하는 기준과 로컬 수정 충돌 처리, 실패 후 재시도 기록을 정합니다.
- **시간 충돌:** 외부 예약과 직접 등록 예약이 겹치면 운영자가 확인할 충돌 상태로 처리합니다.
- **동기화 방향:** 처음에는 외부 예약을 가져오는 단방향 수집부터 검토하고, 외부 예약 생성·수정은 공식 지원 범위가 확인된 뒤 진행합니다.
- **결제 구분:** 외부 예약 수신 자체를 결제 완료로 처리하지 않습니다. 결제 확인과 환불 처리는 별도의 검증 가능한 기록으로 연결합니다.

네이버 계정 비밀번호를 저장하거나 비공식 자동 로그인을 사용하는 방식은 설계에 포함하지 않습니다.
